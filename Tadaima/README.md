# Tadaima! — ただいま！

**Houses and land you'd actually say "I'm home" to.**

Tadaima! researches one city at a time from Japan's public listing portals
(SUUMO, LIFULL HOME'S, atHome, goo住宅・不動産) and ranks each property with
a transparent **worth-a-look score**, so it's easy to decide what's worth a
viewing trip. The name is deliberately not place-specific.

- **Brief for every collection:** houses (new + used) and land/lots,
  ≤ ¥5,000万, ≤ 15 minutes' walk from a station. One flagged exception:
  Kawagoe's Shimohiroya section (added 2026-10-24) deliberately goes
  beyond the walk rule — the page says so, and every card there is flagged.
- **Editions:** Kawagoe · Tachikawa · Tokorozawa · Saitama City · Matsudo · Kashiwa · Hachioji · Funabashi · Utsunomiya · Takasaki · Sagamihara · Yokohama · Machida · Maebashi · Mito · Oyama · Kumagaya · Kasukabe · Koshigaya · Ichikawa · Nagareyama · Fujisawa · Atsugi (23 cities, all live,
  researched 2026-10-23). More cities follow only when their research is done
  to the same standard. Tsukuba was researched and is held: its in-brief stock
  is currently too thin for an edition, and it will be re-checked as stock
  turns over rather than published thin.
- **Home page:** a hub — search by city, station or district, with one card
  per city. Card counts and "from" prices are generated from each city's own
  data file (`build_registry.py`), so the hub can never contradict a city page.
- **Why no Japan map (yet)?** With a handful of cities, a drill-down map is
  three taps to learn how much of Japan isn't covered yet. The map is planned
  for when coverage reaches roughly ten cities across several prefectures.
  That trigger has been reached (23 cities, 7 prefectures), so a List/Map view
  is in design; the cards stay the default, because they carry the counts and
  starting prices a map pin can't.

## The score (out of 100)

| Part | Points | Basis |
|---|---|---|
| Value | 45 | Land: ¥/tsubo vs MLIT transaction benchmarks by station + walk band (Utinokati). Houses: ¥/m² of floor area vs the collection median for new / used. |
| Location | 30 | Station walk minutes + station tier (the city's main Tokyo-facing hubs score highest). |
| Space | 15 | Floor area (houses) or plot size (land). |
| Confidence | 10 | Facts verified on the listing detail page vs taken from a portal index page, and recency. |

A major caution (urbanisation-control area, demolition needed, renovation
project, unknown building condition…) subtracts 7 points and is always
displayed on the card.

## Files

- `index.html`, `hub.css`, `hub.js`, `cities.js` — the hub home page.
  `search-index.js`, `sitemap.xml` and `robots.txt` are generated by
  `../build_registry.py` alongside `cities.js` (hub meta description too).
- `shared/app.js`, `shared/styles.css` — ONE app and stylesheet for every
  edition (since 2026-10-24). Per-city scoring differences (station tiers,
  walk-band benchmarks, Maps query) live in each edition's `data.js`
  `scoring` block, injected by `../apply_site_config.py` from
  `../scoring-config.json`. There are no per-city app.js/styles.css files
  any more — the copies still sitting in this folder on the live site are
  pre-2026-10-24 leftovers that nothing references.
- `<city>/index.html` — each city edition page.
- `<city>/data.js` — the property data the edition loads (same content as the JSON).
- `<city>/data/properties.json` — the same collection as structured JSON, the
  file to edit when refreshing listings.

## Refreshing the data

Re-check each `source.url`, update price/facts/`infoDate` (and
`researchedOn`), regenerate that city's `data.js` from its JSON (its
`build_<city>_data.py` generator writes the `scoring` block too), then run
`../apply_site_config.py` and `../build_registry.py` so the hub, the
property search index and the sitemap stay in sync, and run the smoke suite
(`../test-tools/smoke.js`) before pushing. Properties that have
sold or been withdrawn should be removed rather than marked stale.

## Daily automated refresh

The `Tadaima daily content refresh` GitHub Actions workflow runs daily at
**07:20 Asia/Tokyo** (22:20 UTC the preceding day; GitHub can start it late).
It rechecks unique detail-page sources in all 23 live editions and scans SUUMO
city/ward search pages for new houses and land. It checks up to two new detail
pages per search page per run. This is a bounded discovery scan, not an
exhaustive search of every portal or every results page.

Only unambiguous matching property facts update existing cards. New additions
must meet the edition's budget/walk limits and have single-property area,
construction (houses), source-date and legal fields. They carry the source's
legal text plus an explicit warning that agent confirmation is still needed.
Index-only/shared links and blocked, missing or ambiguous pages retain their
existing facts. An explicit withdrawal notice must be seen on consecutive days
before a record is removed; HTTP errors alone never remove a property.

Each verified record receives `source.checkedOn`; the original editorial
`site.researchedOn` is preserved. The job rebuilds city data, hub counts and
prices, search index, aggregate JSON, metadata and sitemap together, commits
validated changes, then explicitly deploys via the shared Pages workflow.
No paid API or extra repository secret is required.

To inspect coverage, open the workflow's summary and `tadaima-verification-*`
artifact. Failures remain visible; an all-unverified scan fails without changing
the site. Partial scans preserve unverified records. The workflow also offers a
manual **dry_run** input that does not commit or deploy.

Local verification:

```sh
python -m pip install -r tadaima-refresh/requirements.txt
python -m unittest discover -s tadaima-refresh/tests -v
python tadaima-refresh/refresh.py --dry-run --cities kawagoe --max-existing 8 --max-new 1
```

The automated rebuild is implemented in `../tadaima-refresh/build.py`; it
preserves the scoring blocks already committed in each city's JSON. The older
`build_<city>_data.py`, `apply_site_config.py`, `build_registry.py` and smoke-tool
references above describe the original editorial workflow; those scripts are
not present in this repository.
